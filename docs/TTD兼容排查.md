# TTD 与极影视兼容排查记录

更新日期：2026-10-19。已在用户授权的既有极影视反代入口完成单条目的登录、详情与静态播放响应检查，尚未验证成功的 302 云盘直链。没有修改 TTD 配置、监听端口或 NAS 系统设置，没有部署适配层。

## 已确认的证据

- TTD 运行页面显示 v8.8.4。从正在运行实例读取的前端 `static/script.js` 中，测试按钮调用 `POST /api/emby_proxy/config/test`，JSON 字段为 `host`、`proxy_type`、`api_key`。这只能说明浏览器如何把凭据传给 TTD，不说明 TTD 如何把凭据传给上游。
- 浏览器实际捕获：测试接口 HTTP 400，JSON 为 `{"error":"HTTP 404","success":false}`。用户提供的容器访问日志也记录该 POST 返回 400。
- 因此，前端测试接口存在；404 是后端测试流程报告的错误。后续经明确授权使用模拟上游确认了方法、路径和认证位置，见下方记录。
- 日志中 `/api/emby/image/.../primary` 返回 404 是看板海报读取，属于不同请求，不能作为反代测试失败的原因。
- 已查看 TTD 日志中心，当前可见日志没有对应的测试上游详情。未修改日志配置。
- [官方仓库](https://github.com/walkingddd/TgtoDrive)检出的提交为 `f7589e5a2eb1521ed20e9d43306ae900e23a286c`，公开 Python 代码位于 `v6.6.4（最新版请在docker安装）`，没有运行版 `emby_proxy/config/test` 实现。不能用这份旧源码声称已查明 v8.8.4 后端行为。
- [官方使用说明](https://github.com/walkingddd/TgtoDrive#快速部署)要求客户端通过反代端口访问，非 host 网络需映射相应端口；未发现这份说明承诺支持极影视 Emby 兼容服务。

用户已提供的测试结果是：用户令牌放在 `X-Emby-Token` 时指定用户接口成功，放在 `api_key` 查询参数中失败；公开信息接口的 200 不足以证明认证通过。本轮没有重新探测这些 NAS 接口。

## 已执行的两项定点验证

用户明确授权后，单次读取指定条目的用户级详情，禁用重试、不跟随跳转、不请求播放。响应条目标识一致、类型 Movie；顶层 Path 与两个 MediaSources.Path 均为绝对本地形式，含 `@`，没有查询参数或片段；媒体源标为 `Protocol=File`、`IsRemote=false`。未记录真实文件名、路径、Token 或完整响应。

根因是映览将所有含 `@` 的路径一律隐藏，误伤正常目录名，不能归咎于极影视没有返回路径。已改为仅拒绝网络路径主机段中的认证信息，正常本地目录中的 `@` 保留；远程 URL、疑似查询令牌仍不回传。缓存格式升级使旧过滤结果在下次按需读取时失效，不触发全库重扫。相同路径仍去重，同条目多个媒体版本可分别显示；路径是否对应容器、虚拟目录或 NAS 物理目录仍以服务端含义为准。

TTD 的隔离验证没有保存配置，使用假凭据、Mac 临时模拟器和既有测试接口。观察如下：

| 模拟上游响应 | 捕获到的实际请求 | 认证方式 | TTD 测试结果 |
|---|---|---|---|
| 200 | `GET /Users` | `X-Emby-Token`，无查询参数，无 Authorization 身份头 | HTTP 200，`used_path=/Users`，成功 |
| 两个路径均 404 | 先 `GET /Users`，再 `GET /emby/Users` | 两次均为 `X-Emby-Token`，无查询参数，无 Authorization 身份头 | HTTP 400，`error=HTTP 404`，与用户错误一致 |

这证明测试流程依赖用户枚举接口，不是通过 System/Info 或用户名密码登录来判断兼容性，凭据也不是通过 `api_key` 查询参数发送。真实极影视的两个用户列表响应尚未逐个捕获，不能将模拟结果冒充真实上游状态，也不能排除后备路径的错误覆盖前一次错误。当前证据不支持部署“把 api_key 改成 X-Emby-Token”作为测试问题的修复。

另一个限制：模拟器返回的是普通对象，并非真正的用户数组，TTD 仍报告“检测到 0 个用户、成功”，说明测试按钮不足以证明协议完整或播放可用。两个临时模拟服务及本次浏览器会话均已关闭，原反代配置与端口保持不变。

## 既有反代入口定点播放验证（2026-10-19）

用户明确允许在现有极影视反代端口进行登录、指定条目和播放响应验证。账号从映览现有加密配置在内存读取，登录得到的令牌只用于本次诊断，不覆盖持久配置。未读取 TTD 保存的 API Key。所有媒体请求只发往获准的反代入口，无重试、请求间隔至少 2.2 秒、单次超时 15 秒、不自动跟随跳转。

| 验证项 | 实际结果 | 能证明的范围 |
|---|---|---|
| `POST /Users/AuthenticateByName`，设备身份前缀 MediaBrowser | HTTP 200，返回用户标识与令牌 | 通过反代正常登录成功，不等于用户枚举测试通过 |
| `GET /Users/{UserId}/Items/{ItemId}?Fields=Path,MediaSources` | HTTP 200，标识一致，Movie，两个媒体源 | 指定条目详情可读，不代表全库列表已经验证 |
| `GET /Videos/{ItemId}/stream`，指定媒体源、随机 PlaySessionId、`Static=true`、`Range: bytes=0-1023`；令牌仅在 `X-Emby-Token` | HTTP 403，`stage=stream`，错误为缺少 Emby User ID | TTD 此播放校验没有从该请求解析到完整用户身份 |
| 同一媒体源、同一登录账号，在 `X-Emby-Authorization` 中同时包含真实 `UserId` 与 `Token` | HTTP 206，`Content-Type: application/x-cd-image`，没有 Location | 身份拒绝解除；返回原始媒体响应，没有得到 302 |

对应 TTD 日志（仅保留不含凭据的关键文本）：

- 00:17:26：`流请求未解析到 Token`、`X-Emby-Authorization 已收到，但未解析到 Token 字段，has_userid_field=False`、`拒绝缺少 Emby UserId 的播放请求`。
- 00:18:09：`无法获取直链，放行原始请求`，日志中的条目与媒体源标识均对应本次样本。

诊断期间共 1 次登录、2 次同条目详情、3 次同媒体源静态播放请求。中间一次重试因诊断运行器保留了旧闭包，实际仍发送原来的设备身份头，也返回相同 403；不能将它作为“完整身份头也失败”的证据。最后一次将认证头作为显式参数传入，并核对实际发送字段名，才是完整身份头的有效验证。未调用 PlaybackInfo、播放进度上报、转码启动或媒体修改接口。对媒体响应在取得响应头后取消响应体，没有保存视频内容或请求其他 NAS 端口。

两个媒体源的元数据均为 `Container=iso`、`Protocol=File`、`IsRemote=false`；Path 未显式以 `.strm` 结尾，也没有 DirectStreamUrl / TranscodingUrl。这只能说明本次接口如何表示资源，不能证明 NAS 上原始文件一定不是 STRM，更不能推广为所有极影视 STRM 都无法重定向。本次也未验证播放器解码或持续播放。

请求依据为 [Emby 官方视频流说明](https://dev.emby.media/doc/restapi/Video-Streaming.html)：使用文档定义的 `/Videos/{Id}/stream`，传 MediaSourceId、PlaySessionId 与 static 参数，没有枚举猜测其他播放路径。当前不需要为映览增加播放接口；本次诊断独立于只读看板。

## 下一步边界

已向用户请求一条确认由 TTD 生成 STRM 且入库极影视的条目 ID，以及针对该条目的同范围验证授权。取得后仅验证该样本，不扫库寻找、不修改 STRM 或云盘文件。当前样本的结果不足以选择认证适配层、路径适配层或部署方案。

用户指出经过 TTD 的 302 会有日志；本次确实通过日志与实际响应对应确认了回退原始流。原生极影视播放器入口、请求路由仍未提供，因此未验证原生播放器是否经过反代。日志中出现对应 302 事件可以支持路由判断，但没有日志不能单独证明请求没有经过 TTD，也可能已经进入反代但未生成直链。尚不部署仅为让用户枚举测试变绿的适配层，也不为匿名请求注入固定 Token。

本地诊断工具为 `scripts/ttd-probe.mjs`，不属于映览运行服务，也不在启动时自动运行。默认只监听本机随机空闲端口；10 分钟自动关闭。允许来源必须是一个明确 IP，证据接口只允许本机读取；不转发请求，不读取媒体，不保存原始请求或凭据值。

```sh
# 仅在明确同意隔离测试后运行；所有地址以当时环境为准。
PROBE_HOST=0.0.0.0 ALLOWED_CLIENT=<TTD容器对Mac可见的来源IP> node scripts/ttd-probe.mjs
```

可设 `PROBE_STATUS=404` 仅模拟上游 404，以观察后备路径；默认是 200。证据读取接口不受该模拟状态影响。

终端会打印临时端口和明确标识为假的诊断凭据。调用已确认的 TTD 测试接口时，仅为本次测试传入模拟器地址与假凭据，不调用保存或应用接口。测试后从本机 `http://127.0.0.1:<临时端口>/__probe/evidence` 读取方法、路径、查询字段名及认证头是否存在，然后终止诊断器。模拟器返回成功不代表真实媒体服务器或 302 链路可用。

## 真实播放验收边界

- 登录成功、列表成功、播放成功、302 直链成功需要分别验证。
- 获取到 302 后还需确认目标是预期云盘直链、没有向第三方泄露媒体服务器认证头，客户端实际能获取媒体内容；不能只看测试按钮变绿。
- 极影视原生播放器若继续走自身原生 API / 播放地址，TTD 反代不会自动接管它。必须先证实该播放器能配置代理入口，或原始播放链路本身会访问已有 STRM 中的 TTD 地址；否则 Emby 客户端经过反代的结果不能推广到原生播放器。
- 当前未修改 STRM、云盘文件或刮削数据；已检查单条目的静态播放响应，没有获得云盘直链，没有进行新增 Docker 部署。正常 Emby 反代入口未访问、未修改，自动更新总开关仍为关闭。

## 映览读取的影响

映览不调用远端媒体修改、删除、扫盘或刮削接口，但只读并非零负载：请求会占用网络、数据库查询、CPU、缓存与日志空间；服务端实现还可能在生成元数据时访问存储。未测量极影视或 Emby 的实际 CPU / 内存峰值，不能保证完全不影响其他任务。

当前自动更新总开关已关闭，包含轻量更新、完整校准和季集补全。浏览已有缓存不触发片库更新；主动点详情或加载尚未缓存的海报仍可能请求远端。首次完整建立片库和手动完整校准会读取全库元数据，应在用户确认后按需执行。
