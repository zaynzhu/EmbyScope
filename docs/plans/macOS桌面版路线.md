# 映览 · EmbyScope：macOS 桌面版路线

日期：2026-10-21。依据版本：`5b248ae`，研究开始时工作区干净。

状态：研究与执行路线，尚未实现桌面原型、迁移数据或构建 DMG。本文不是启动实施或访问 NAS 的授权。

## 目标与已确认取舍

用户已确认：Mac 优先；保留现有网页版，暂不要求同步新增功能；窗口经常开着，切回来要立即看到片库。希望改善 UI，并降低长期运行时的内存占用。

沿用业务边界：本地单管理员、多 Emby／极影视连接、仅展示可访问的信息、来源与路径对照、保守去重、NSFW 遮挡、SQLite、加密保存凭据。自动更新当前关闭，迁移不得擅自开启。不得改变 TTD 配置、现有反代或端口；访问 NAS 仍遵守用户的定点授权。

成功不能仅定义为“生成 DMG”：需在用户 Mac 上独立启动、无需安装 Node，窗口常开时响应及时、内存可解释且有界，现有兼容行为和数据安全没有退步。

## 推荐判断

**优先验证 SwiftUI 原生界面 + 现有 Node 业务内核 + SQLite。**

- SwiftUI 承担桌面布局、窗口、快捷键、海报展示和状态恢复。界面重新设计，不加载现有网页作为主界面。
- Node 继续负责 Emby 通信、限流、兼容差异、去重、资源信息、安全过滤和 SQLite 写入。Swift 不再实现另一套 Emby 客户端，也不直接写数据库。
- 应用内附固定版本、匹配架构的 Node 运行时。优先验证运行时与 JS 资源一起内置的简单方案，不以将 JS 编译成单个可执行文件为前提。
- 桌面应用管理一个 Node 子进程，通过仅本机可访问的接口使用现有业务能力。接口、进程和数据目录都独立于正在运行的网页版。

这是基于 Mac 优先、界面需要重做、窗口长期打开的建议，不是“原生必定低内存”的结论。它增加一套 Swift UI 和发布维护工作，但保留已验证的业务内核，控制同时重写的范围。

| 路线 | 对当前目标的价值 | 主要代价／选择条件 |
| --- | --- | --- |
| SwiftUI + 现有内核 | 原生桌面交互；主界面不需要 WebView；兼容规则复用 | 需要新写 UI、管理辅助进程；优先验证 |
| Tauri + 现有内核 | Web UI 复用更多，支持系统 WebView 与辅助进程 | 窗口常开仍有 WebView 和 Node；若原生 UI 投入无法接受，可回到此路线 |
| SwiftUI + Swift 全重写 | 最终可减少运行时种类 | 要重验极影视、限流、身份、去重、缓存与迁移；只有确认 Node 是无法优化的主要瓶颈时再讨论 |
| Electron | Web 复用与生态完整 | 本项目没有必须依赖它的能力；暂不新增此路线的验证投入 |

早期考虑过“关闭窗口后释放 WebView／Node”的 Tauri 路线。用户明确窗口经常开着后，它只能是补充优化，不能支撑主要内存目标。不得通过切回时重建片库来实现漂亮的待机数据。

## 当前依据与实际测量

代码证据：

- [store.js](../../src/store.js)：使用 `node:sqlite`，数据库为 `embyscope.sqlite`，WAL 模式；`secret.key` 用于 AES-256-GCM 凭据加密。这不是全库加密。
- [service.js](../../src/service.js) 的 `library()`：先解析所选服务器的完整 catalog，合并、分组去重、过滤排序，最后分页。因此返回 24 条不代表只处理 24 条。
- [identity.js](../../src/identity.js)：跨编号合并后检查冲突；按媒体类型和标识处理，不按同名合并。编号冲突与查询服务器范围有关，不能简单用全局去重结果代替所有筛选结果。
- [server.js](../../src/server.js)：目前是 Web 服务入口，默认监听全部地址；已有关闭及任务等待逻辑，需要验证桌面生命周期，不能直接照搬为合格的桌面入口。
- 现有图片缓存有磁盘容量上限，但磁盘缓存容量不等于 UI 解码后的内存占用。

本次只读测量：未请求 NAS，也未输出标题、资源路径或凭据。

| 条件 | 结果 | 能说明什么／限制 |
| --- | --- | --- |
| 当前本地 Node 服务的一次 `ps` 采样 | RSS 44,224 KiB，约 43.2 MiB；CPU 当时显示 0.0% | 单次空闲样本，不是完整 App 内存，也不能证明持续零 CPU |
| SQLite 只读聚合 | 两份 catalog JSON 共 7,860,586 字节；141 份图片共 16,929,996 字节；自动更新关闭 | 是当前样本的存储规模，不是内存 |
| 新 Node 进程只读调用一次现有 `library(all, page=1)` | 返回 24 条，共 8,482 个分组；约 178.7 ms；RSS 从 42.8 到 118.0 MiB，heapUsed 从 4.8 到 42.3 MiB | 说明查询有明显分配；没有测 GC 后驻留、完整峰值或 UI，不能外推为 App 的稳定内存 |

上述第三项使用 `DatabaseSync(..., { readOnly: true })` 和仅提供公开服务器元数据、缓存读取的 Store 适配器，实例化 `Service(store, null)`；调用前后读取 `process.memoryUsage()`，以 `performance.now()` 计时。进程没有启动 HTTP 服务、调度器或 Emby 客户端。不是生产性能基准，也没有保存实验程序。

环境：本机 arm64、macOS 26.6.2；找到 Swift、Rust 和 Command Line Tools，但没有编译验证桌面工具链。项目使用 Node 22.22.2，当前没有第三方运行依赖。完整 Xcode、签名、辅助进程分发均未验证。

## 结构决定的对抗性审查

### 🔴 致命弱点（必须解决，否则整体失效）

**把原生 UI 当作低内存证明。**

- 问题：原生 UI 仍需解码图片、保存视图状态，Node 仍会全库分配。
- 为什么致命：如果只展示空窗口内存，就没有验证用户长期打开真实片库的目标。
- 证据：当前仅一次本地分页查询便有明显 RSS 增量；这部分与 UI 框架无关。

修正：先验证带缩略图、分页、同作品对照的窄范围原型；以 App 与辅助进程整体数据为依据。未通过前不全面迁移。

### 🟡 主要缺陷（应该解决，影响质量和可信度）

| # | 缺陷 | 严重程度 | 简要说明 |
| --- | --- | --- | --- |
| 1 | 混合技术栈增加发布工作 | 高 | Node、JS 资源、SQLite 和签名要在无开发环境的启动路径上验证 |
| 2 | 本机 HTTP 不天然可信 | 高 | 随机端口不等于认证；必须限制来源及访问，不能移除本地管理员边界 |
| 3 | 原生组件不自动解决设计问题 | 中 | 需用真实任务验证层级、路径对照和信息密度，不能只是换控件 |
| 4 | 只测一次内存会误判 | 高 | 需要反复翻页、静置、缓存冷暖、重开及更大模拟库 |
| 5 | 省内存与立即恢复冲突 | 中 | 不能在窗口仅失焦时清掉当前页或重启后台 |

### 🟢 改进建议

1. 先证明一个完整的桌面切片：离线模拟数据 → 内置 Node → SQLite → 原生海报页 → 详情对照。
2. UI 只保存当前页和有上限的邻页／缩略图缓存；后台只保留必要业务状态。失焦不重建页面，不触发全库刷新。
3. 分开测 UI、图片解码与 Node 查询；只优化证据指向的部分。不得先把所有 JavaScript 改成 Swift 或 Rust。
4. 新桌面入口与 Web 入口隔离；数据迁移采用副本与可回退方案。

### 📋 审查总结

- 整体评估：保留业务内核、原生重做界面的方向符合已确认偏好，但性能和独立分发仍是必须验证的前提。
- 最高优先级行动：用模拟库做带图片和真实数据通路的最小原生原型，测窗口常开时的表现。
- 如果不改：可能只得到一套成本更高、仍然全库加载的漂亮界面。

## 首个可执行阶段：验证原生界面与业务内核能否共存

前置条件：用户另行授权开始实现。先重新读取项目规则、工作区状态和本文件；不访问 NAS。允许新增隔离的 `desktop/` 原型与模拟夹具，不迁移真实配置，不改变旧 Web 服务启动方式。

第一步：确认本机 Swift/macOS SDK 能编译、启动最小窗口，再验证应用内置 Node 在受控 PATH 下运行现有 `node:sqlite`、建表、读写、关闭和重开。工具缺失按受阻记录，不安装大体积工具或假称成功。

接着完成以下窄范围切片：

1. 一个 SwiftUI 窗口，服务器筛选、海报分页、搜索、详情侧栏；只接模拟数据。
2. Node 业务核心独占测试数据库；独立桌面入口监听 `127.0.0.1` 的动态端口，明确 readiness、进程退出、错误和重试行为。端口不是密钥，日志不得输出凭据。
3. 保留本地管理员认证；Swift 客户端管理自己的会话，修改操作的来源／CSRF 校验不能为兼容桌面而删除。不让其他本地网页绕过认证。原生 UI 输入连接密码后仅通过本地受保护通道交给内核；用户令牌不作为展示 API 的输出。
4. 海报按显示尺寸解码、限制并发与内存缓存；分页不把全库模型送进 Swift。NSFW 遮挡由明确状态控制，不在切换服务器时意外暴露。
5. 窗口打开或失焦时保持当前页和内核可用；自动更新关闭时不因聚焦重新扫描。退出应用时停止接收任务、收尾／取消在途请求、关闭数据库并回收子进程。单实例机制防止两个内核写同一数据目录。

验证输入与预期：

| 输入／操作 | 预期 |
| --- | --- |
| 两服同 TMDB 同类型作品、不同 ItemId | 汇总同作品对照列出两条来源；单服视图只列本服记录 |
| 同服或跨服编号冲突、同名缺编号 | 按现有保守规则独立，不误合并；不同服务器筛选范围遵循原语义 |
| 同一条目有两个媒体源路径 | 显示一个条目下的两个资源位置，不能说成重复入库两次 |
| 一服权限不足、一服离线但有旧缓存 | 缺失不当零；显示来源、缓存时间与异常，另一服可用 |
| 翻页、搜索、返回详情、切换 App | 页码与上下文保留，已有内容立即可见，不等待远端扫描 |
| 更新或图片请求中退出／重新启动 | 无孤儿进程、无损坏数据库、无任务继续偷偷访问外部服务 |

性能与发布验收：

- 使用固定模拟数据，至少覆盖约当前规模及更大规模；记录条目数、图片数量／尺寸、页面大小、版本、构建方式和机器条件。
- 用 Release 配置记录冷启动、缓存暖启动、静置、连续翻页与详情开关。至少连续 20 轮交互并静置观察；记录每轮及结束后数据，排查持续增长，不把正常缓存增长直接叫泄漏。
- 记录 Swift 主进程和 Node 辅助进程，说明 RSS 与 macOS 内存占用指标的区别；不能只报主进程，不能将不同指标直接比较。通过 Instruments／系统工具定位分配及持有对象。
- 切回 App 不重建当前页；记录重开窗口和首次启动的实际延迟，不能混为“秒开”。
- 内存和启动时间预算尚未由用户确定。首阶段报告提供实测范围与主要来源，作为是否进入完整 UI 重写的依据，不承诺几十 MiB 或固定排名。
- 用不包含用户 fnm／系统 Node 的受控 PATH 启动应用，验证资源定位与 `node:sqlite`；真正干净机器、签名公证和 DMG 安装仍是后续项目，不能宣称此时已验证。
- 修改共享内核时运行 `npm run check` 和 `npm test`，补生命周期／认证／数据行为相关测试。原型构建与运行结果单独列出；旧 Node 测试通过不代表原生 UI 已通过。

## 后续方向及改向条件

首阶段通过后，先定桌面交互再扩完整功能：固定侧栏、简洁概览、海报片库、同作品记录对照、服务器及更新设置。对照视图以来源服务器、条目、资源位置为主；“多条记录”不等于重复文件，路径缺失就明确标注，不能推断物理文件数量。可复制用户有权查看的路径，不新增远端操作。

查询优化按实测分层推进：先定位重复 JSON 解析与分组成本。若持续影响响应和内存，再把必要条目与索引规范化到 SQLite，缓存可重复使用的分组结果；不得用永久保留整个对象图简单换速度。分组缓存必须按服务器选择范围与数据版本失效，编号冲突、桥接编号和详情全服范围要有回归测试。涉及 schema 变更时先提供迁移、回退和语义一致性证据。

保持唯一的调度实现。自动更新默认关闭；开启后后台更新仍由 Node 限流执行，同服务请求至少间隔两秒。窗口常开不等于持续联网，不因每次打开详情重扫全库。不为降低待机数字另写一套 Swift 定时同步逻辑。

真实数据只在后续授权下导入独立的 Application Support 目录。复制时保证 SQLite 一致性并带上加密密钥，不在运行中只复制主数据库文件；保留原数据与回退路径，不能让 Web 和 App 同写一份库。

最终再处理 DMG、签名及更新分发。本机优先 arm64；是否支持 Intel Mac、最低 macOS 版本、是否需要公证分发尚未决定。NAS 的 `linux/amd64` 要求不适用于 Mac 应用。内置 Node 及所有辅助可执行文件的架构、许可和签名均需验证，不要求用户关闭系统保护。

以下证据需要重新判断，而非硬推原路线：

- 用户改为要求 Web 与桌面 UI 长期同步：重新比较 Tauri 的收益。
- 原生界面开发代价超出可接受投入：可选择 Tauri 重做 UI，但必须保留窗口常开的性能验收。
- Node 成为主要且无法在当前边界内优化的常驻开销：讨论局部原生化，不直接批准整套重写。
- 内置 Node／SQLite 或签名分发无法成立：先隔离具体失败点，再评估打包替代；不能暗中要求用户另装运行环境。
- 需要改变去重、权限、NAS 访问、更新默认值或远端只读边界：停止受影响部分，带证据交回判断。

## 官方依据与未验证项

- [Apple Process](https://developer.apple.com/documentation/foundation/process)：支持启动和管理独立子进程，可作为保留 Node 内核的基础；沙盒约束另需核对，不代表打包已成功。
- [Apple LazyVGrid](https://developer.apple.com/documentation/swiftui/lazyvgrid)：按需创建网格视图；不能据此假设图片缓存也自动有界，小页数是否需要它由测量决定。
- [Apple 内存测量](https://developer.apple.com/documentation/xcode/gathering-information-about-memory-use)：用内存图与分配记录追踪占用来源，支持上述测量方法，不提供本项目的内存承诺。
- [Tauri 进程模型](https://v2.tauri.app/concept/process-model/)及 [Node 辅助进程](https://v2.tauri.app/learn/sidecar-nodejs/)：备选路线具备基础能力；示例不能证明现有 `node:sqlite` 可直接打包。
- [Tauri macOS 签名说明](https://v2.tauri.app/distribute/sign/macos/)：区分本地签名与公证分发；本文未完成任何签名验证。

目标、关键思路与验收要求一致时，可自行做局部可逆调整并记录理由。局部实现错误自行修复并验证；可能改变关键结果的偏差向用户询问。

进入已标注未知区域时，提示用户选择当前执行者继续探索或交回分析。缺工具、信息或数据时标记受阻，不能当成验证通过。核心假设被推翻，或必须改变关键业务要求、架构边界、验收标准时，停止按受影响路线实施，带证据请求重新判断；只暂停受影响部分。

新证据可以挑战原方案，不能降低验收标准来通过检查。常规工作凭既定标准和实际证据结束；遵守本路线规定的交回审查条件，不自行免除，无需每阶段例行交回。交回包括预期、实际、复现证据、已尝试内容、受影响假设和待决定问题。完成时记录实际产物、调整理由、验证及剩余问题。
