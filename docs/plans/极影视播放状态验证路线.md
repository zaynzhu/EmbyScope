# 极影视播放状态验证路线

2026-10-23，初始适用于提交 8831819 后的工作区。已完成下述 VidHub 只读对照；未修改应用运行代码，尚未验收兼容检测功能。

## 真实对照结果（2026-10-23 01:09–01:20，Asia/Shanghai）

用户分两次明确授权，第一轮 12 次、第二轮 9 次。使用当前极影视账号的用户级 Items/Resume，Limit=18、EnableUserData=true；不重新登录，无重试及重定向，不扫库，不读取海报/播放接口，不访问 TTD 或管理端口。用户逐阶段确认 VidHub 的动作后才取样；请求均 HTTP 200，最短间隔 15.100 秒，每次返回 2 条。两轮独立诊断进程均正常退出，授权次数耗尽后没有继续请求。

另一条历史记录在全部 21 次中保持原位置和日期不变。原始响应的条目层没有 PlayState/IsPlaying 等明确状态；UserData 的字段为 PlayedPercentage、PlaybackPositionTicks、PlayCount、Played、IsFavorite、LastPlayedDate。Played 表示观看完成情况，不能作为正在播放。

LastPlayedDate 的 UTC 标记值相对取样 UTC 时间约超前 8 小时，其显示钟点接近本地墙钟。这里只记录时间表达异常，未检查 NAS 时钟或证明原因；实现不能直接拿此绝对时间减本机 now 判定新鲜度，也不能未经验证硬减 8 小时。应使用本机接收时刻与连续字段变化。

本次支持“当前账号可读记录中存在连续播放活动线索”，不能证明精确停止事件、暂停/退出区分、全部播放器、所有媒体或并发设备。冷启动、片头/片尾续播阈值、缓存延迟、拖动与后台同步尚未验证。Resume 中没有某条不能证明它没在播。

已向用户提出的产品取舍：若接受明确标注的兼容检测，可显示“检测到播放活动”和“未检测到播放活动”，暂停/退出均视为无继续播放活动；错误为未知。预计开始识别约 15–30 秒、无更新约 60 秒结束活动提示，均为待实现验证的建议值，不是本轮测出的产品 SLA。

用户明确选择：先确认无法取得明确播放状态，再接受兼容检测。因此目前没有获得直接以推断替代状态的同意，暂停兼容检测产品接入，继续检查有协议依据的事件通知来源。不能将这个条件同意解释成现在就实现推断，也不能用有限的接口失败证明所有未知通道绝对不存在。

诊断脚本位于忽略目录 test-output/probe-resume-state.mjs 与 probe-resume-pause.mjs；默认仅模拟，不会联网。模拟验证覆盖限定 GET、禁重定向、18 条上限、显式身份不匹配拒绝、输出脱敏以及零/null/false 区分；真实标识仅用随机别名，原始响应与凭据未保存。脱敏时间序列不含片名、路径或令牌，未写入产品缓存。已消费的 --execute-authorized 运行模式不得复用为新的真实请求授权。

## 目标与调整后的判断

### 标准 WebSocket 入口限定验证（2026-10-23 01:26，Asia/Shanghai）

用户另行授权一次握手。对极影视 8021 服务根路径发起 HTTP Upgrade，查询串仅含诊断 deviceId；已保存令牌仅放 X-Emby-Token，沿用 MediaBrowser 身份头。12 秒超时，不重试、不跟随跳转、不换路径、不订阅消息、不发送播放控制命令。实际请求一次，返回 HTTP 404，连接关闭，诊断进程正常退出。授权已消费，不得再次执行真实模式。

本机模拟此前已覆盖有效 101 与普通 404 两种响应、Sec-WebSocket-Accept 校验、令牌不进入 URL、请求次数及立即关闭。脚本 test-output/probe-zspace-websocket.mjs 默认只运行本机模拟；未修改应用运行代码或真实缓存。

结论限于“标准根入口搭配本次请求头认证没有升级成功”。官方文档示例使用查询参数 api_key，而本次为避免令牌进入 URL 使用请求头；HTTP 接口接受该头不证明 WebSocket 同样接受。因此不能从一次 404 推导所有路径、认证方式或极影视原生协议均不支持实时状态，也不能据此降低认证边界、枚举路径或把令牌改放查询串重试。

结合两种 Sessions 路径均 404、续播字段没有明确状态，目前已检查的普通账号读取方式没有可用的确定状态来源。若后续获得极影视官方事件入口及安全认证依据，可重开该分支；在此之前停止盲试。兼容检测仍只能报告连续观看活动线索，不能宣传为确定的“在播/没播”。用户的条件同意不应被表述为已验收或已启用此功能。

用户现在需要知道极影视是否在播、在播哪个作品，不要求显示进度；原 Emby 的现有实时展示继续保留。用户已拒绝要求 TTD 新增功能以及新增中转的两条路线，不再将其作为待用户选择的推荐方案。

必须保持原反代、端口、播放器地址和自动更新设置。不能把“最近请求播放”替换成“正在播放”，不能把观察失败当成没播。先验证不改变播放路径的数据来源，不预先建设适配层。

此前由两种 Sessions 路径返回 404 直接收窄到修改 TTD/新增中转，判断过早。这只排除了两个已测试的查询入口，尚未检查账号条目返回值中的全部状态字段及其时间变化，也没有证明独立事件通知通道不可用。

## 已有依据和可信范围

- `src/playback.js` 当前仅从 GET /Sessions 读取会话。已有实测原 Emby 返回有效当前用户会话，极影视两种路径均 404。
- `src/service.js` 已读取用户级 Items/Resume，极影视历史限定验证返回 200、有 1 条。不能把该历史响应直接当作现在仍可读。
- `src/identity.js` 将 UserData 中的 PlaybackPositionTicks、LastPlayedDate 规范化后保存，未保留任意额外状态字段。因此本地缓存不能回答原始响应是否存在自定义实时字段；没有证据说明这种字段实际存在。
- 用户容器访问日志说明测试期间存在周期性进度 POST。没有正文、端口或规则，不能确认对应条目的状态，也不证明保存位置实时更新。
- [MoviePilot 极影视实现](https://github.com/jxxghp/MoviePilot/blob/v3/app/modules/zspace/zspace.py)明确读取用户 Resume 列表；该实现只证明有续播读取路线，不证明实时状态。
- [Emby 官方 WebSocket 文档](https://dev.emby.media/doc/restapi/Web-Socket.html)另有 UserDataChanged 通知。该事件也包含评分等个人数据修改；Playstate 是远程控制命令，不能当成另一播放器的播放状态报告。官方示例使用 URL 查询令牌，极影视已知 HTTP 查询令牌认证存在差异，不直接照搬到真实服务。
- 本轮 Tavily 检索未找到高可信的极影视实时会话/事件适配实现；普通 Emby 文档不能当作极影视已支持的证据。官方页面链接的旧 ApiWebSocket.cs 源文件当前返回 404，未以其内容作推断。

## 首个可执行阶段：原有账号读取接口的受控对照

目的不是“通过位置变化证明一定正在播”，而是先回答：是否漏读现有状态字段、观看数据在什么时候更新，以及这些观察能否区分播放与结束。

前置条件：另获用户明确同意限定 NAS 访问，并由用户操作一个播放器的播放与停止。只使用已保存普通媒体账号，不重新登录，不读取 NAS 管理账号，不请求 TTD 管理凭据。

1. 通过当前连接的用户级 `Items/Resume` 路径 GET，沿用现有项目的 EnableUserData 参数，Limit=18。不给请求添加猜测性的路径或字段选择参数。
2. 总计最多 12 次、相隔至少 15 秒、单请求超时 12 秒、单连接最多 1 个在途请求、禁止重试和重定向。遇到认证失败、响应过大或格式不符停止。不遍历分页，不扫片库，不读取海报或媒体流。
3. 分为未播放、用户明确开始播放、用户明确退出播放三个阶段，各最多 4 次。下一阶段必须等用户报告实际动作，不把等待时间当成动作已经完成。记录实际动作与取样时间，不要求用户精确掐秒。
4. 原始响应只在内存处理。先保留字段名称/类型，状态候选只从条目级和 UserData/PlayState 中提取布尔状态、安全数字位置和时间；媒体标识仅在内存用于跨样本配对，输出用本次随机别名。片名仅在确认目标时短暂核对，不保存路径、签名链接、令牌或完整报文。
5. 区分字段缺失、null、0、列表消失、错误和空列表；未知字段值不直接打印。只读打开本地配置，不写产品缓存、不恢复调度。

### 首阶段结果如何决定下一步

| 实际观察 | 可以得出的结论 | 后续动作 |
|---|---|---|
| 有明确状态字段，开始/结束随真实动作变化 | 存在值得验证的候选来源；字段名本身还不证明语义 | 再验证暂停、拖动、切片和另一个播放器，测延迟与身份范围 |
| 只有位置/时间在播放时连续变化 | 有观看活动的候选证据，不能直接得到准确的结束状态 | 不接入确定的“在播/没播”；保留为研究结果，判断有无可靠停止信号 |
| 只在退出时更新 | 适合续播记录，不适合当前目标 | 结束这条路线，不用提高轮询频率掩盖问题 |
| 条目不在 Resume 列表 | 可能因续播阈值、完成度、排序或实现差异 | 不推断为没播，也不扩大为全库扫描；单条详情后续需单独确认 |
| 错误、缓存不变或空响应 | 无足够观测 | 标记未知，不当作未播放 |

第一阶段只决定是否值得继续；不能用一个客户端、一个影片、一次变化判定全部兼容。样本受其他设备或进度同步干扰时，应重做受控对照，不按观察顺序硬配身份。

## 另一个待验证方向：独立事件通知

若账号读取数据不足，检查已有协议依据能否支持极影视的事件订阅。这与增加播放中转不同：观察者直接连接媒体服务，不改变播放器路径。

已按用户单次授权完成上面的根入口握手，HTTP 404，未建立 WebSocket。当前仍没有极影视支持事件订阅的证据，不继续枚举 URL，不将 Token 放入可能记录访问日志的查询串。后续只有获得新的明确入口及安全认证依据、用户同意后才继续真实连接测试。

连接成功也不等于成功获取播放状态。只有评分/续播变更通知不够；必须能可靠绑定当前账号与媒体，并识别开始/结束或取得完整活跃状态快照。连接断开应显示未知。不得发送播放、暂停、停止、模拟心跳或其他遥控命令。

## 产品接入的验收门槛

- 真实动作对照覆盖播放、暂停、恢复、退出、换片及网络异常，并明确“暂停算在播会话还是单独状态”；未作业务决定前沿用原 Emby 的独立暂停状态。
- 不仅有“在播”的正证据，还要有清晰的退出依据；仅位置不动、列表消失、请求失败均不够。
- 测出可解释的检测延迟后再与用户确认；不得预先承诺秒级或完全实时。
- 至少两个用户实际使用的播放器分别验收，其他未测客户端及极影视原生 App 单列未验证，不宣传全部覆盖。
- 当前账号、服务器、媒体严格隔离；如果源仅有账号级聚合，不虚构设备名或并发会话。
- 获取成功且结果权威为空才能显示未播放；无法判断时保留未知。
- 用实际验证结果决定是否编写适配，不为展示效果降低证据门槛。当前尚未达到这些条件。

## 对抗性审查

### 🔴 致命弱点

位置变化不能单独等同于播放：手动拖动、离线同步、延迟写回也会改变它。位置不动更不能等于停止，暂停或服务端缓存就是反例。若来源没有足够信息，这条路线无法满足确定的二态状态，必须停止按该假设实施。

### 🟡 主要缺陷

| 风险 | 约束 |
|---|---|
| 把自身查询导致的账号 LastActivityDate 更新当成播放器心跳 | 账号在线/活动时间不作为播放证据 |
| 把 Resume 中已有条目当作活跃状态 | 比较用户真实动作和字段含义，静态存在不算在播 |
| WebSocket UserDataChanged 或 Playstate 名称被误解 | 变更与遥控命令分别处理，不冒充状态通知 |
| 把根入口的请求头认证握手 404 推广为极影视全面不支持 WebSocket | 仅记录本次组合失败；路径、认证、实现差异尚不能分别归因 |
| 为获得理想结果无限加频率/扫库 | 固定次数上限，不满足即记录失败或未知 |

### 🟢 改进建议

先做有限的读取对照，只有明确候选状态才继续真实边界测试；事件通知是待证分支，不是已经成立的替代方案。

### 📋 审查总结

尚有低侵入的验证方向，前两条改造路线并非唯一逻辑可能；但新方向目前也只有验证价值，不能承诺一定解决。

## 接手约定与启动指令

接手先核对当前代码、目标、用户最新授权及已执行请求次数，不重复消耗旧授权。普通可逆细节可自行调整并记录。首次新增 NAS 请求、扩大数据范围、改变精度/实时语义、修改播放路径或要求新凭据时，停止依赖部分并明确交回。进入未知分支不能以猜测接口替代依据。完成或受阻时报告预期、实际、样本范围、响应证据和剩余假设，不把原型当正式功能。

可转发启动指令：请阅读 `docs/plans/极影视播放状态验证路线.md`，作为当前执行者接手。先核对限定只读验证是否已获用户授权；无授权只准备本地诊断，不访问 NAS。有授权后按第一阶段做真实动作对照，达到次数上限即停止。根据判定表报告是否存在可继续验证的来源，未通过产品门槛不要接入确定的“在播/没播”。不启动其他执行者，不更改原反代或客户端。
