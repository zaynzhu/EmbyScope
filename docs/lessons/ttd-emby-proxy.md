# TTD Emby 兼容反代：分层定位

**结论速览：**先区分测试接口、账号认证、STRM 取链、代理 302 和媒体读取；本项目已有成功样本，不需要凭测试 404 就部署适配层。
**适用条件：**2026-10-18 至 2026-10-23 的既有 TTD / 极影视环境；完整解码、原生播放器路由及所有客户端未全面验证。

## ✅ 用运行行为确定测试流程，而非猜 Token 或路径（2026-10-23）

- **环境：**macOS 客户端，TTD 当时页面显示 v8.8.4；极影视启用 Emby 兼容服务，固件版本未采集。
- **为何值得记：**经历测试 404、认证猜测、ISO 样本和静态流回退等多轮排查，容易误改本来正常的反代。
- **最终方案：**复用已查明的流程与证据层级，完整实验方法只在 [TTD 兼容排查](../TTD兼容排查.md) 维护。运行前端调用的是：

```text
POST /api/emby_proxy/config/test
{"error":"HTTP 404","success":false}
```

- **为什么这样做：**HTTP 状态为 400、正文写 HTTP 404，说明前端测试路由存在，404 来自后端测试流程；不能据此确定具体真实上游响应或 Token 无效。
- **验证证据：**原记录的假凭据模拟上游验证：TTD 先 `GET /Users`，失败后 `GET /emby/Users`，使用 `X-Emby-Token`；两路径 404 时复现上述返回。另一轮指定 STRM 完整流程取得 PlaybackInfo 200、代理流 302、明确返回 CDN 的前 1 KB 为 206。没有修改规则或端口。
- **关键步骤：**先确认运行版前端/日志 → 授权的假凭据模拟 → 确认样本是 STRM → 使用真实客户端所需身份与播放信息 → 分别验证重定向和有限媒体读取。不要复制或转发 Emby 凭据到 CDN。
- **易错点：**直接地址返回 302 不等于反代返回 302；媒体 206 不等于 302；两服可分别播放不证明任意并发条件稳定。原服务和关联反代属于同一连接，不重复建库。
- **交叉验证：**历史实机与模拟记录由当前会话引用原文核对；本轮单 agent 文档复核，非多 agent 精粹。证据入口同上及 [原验收记录](../验收记录.md)。

## 🔶 原生极影视和未覆盖客户端是否经过反代（2026-10-23）

- **环境/交叉验证：**同上；本轮仅核对既有记录，没有新增实机实验。
- **当前推断：**成功反代样本及用户“三种云盘均能播放”的反馈不能证明原生播放器的全部请求经过该入口。
- **已到哪一步：**指定 STRM 的完整 302 链路已验证；完整解码、持续播放和原生客户端路由未全面验收。
- **下一步验证动作：**获得新授权后，只核对指定客户端实际服务器入口与指定样本响应；不扫端口、不改现有链路。
- **为何值得继续：**避免把普通 Emby 兼容客户端的成功外推到 NAS 原生播放器。

## ⛔ 把云盘刷新令牌失败、非 STRM 或用户枚举失败归为双反代冲突（2026-10-23）

- **环境/交叉验证：**当时运行版 TTD，用户提供的日志和纠正；单 agent 核对，来源为用户粘贴与原诊断文档，未获得全部内部源码。
- **报错原文（用户日志的无敏感片段）：**`HTTP 400, code=4126, message=The refresh token is incorrect or expired`。
- **报错稳定片段：**`code=4126`、`The refresh token is incorrect or expired`；不保存资源 ID、完整播放地址或 Token 指纹。
- **错误原因：**该日志明确是光鸭取链刷新凭据错误；最早另一个失败样本后来被用户确认为非 STRM。这两项都不证明只能运行一条 Emby 反代。
- **为何不可再采用：**不同层的失败不能靠改端口或替换 Emby Token 统一解决；测试流程已发送 Token 请求头，盲加“查询参数转请求头”适配没有证据支持。
- **替代方案：**按本页成功条目分层验证；账号重登录或凭据修改由用户另行决定。
- **判定时效：**仅对应上述日志和 2026-10 的实现；升级后重新核对，不宣称所有 code=4126 都有相同成因。
