# 豆瓣同步与海报补全的任务衔接

**结论速览：**已看记录整批提交后，用本次 ID 集合接续独立补图任务；图片失败不回滚短评或检查点，已有图片不重复下载，配置 S3 时继续镜像。
**适用条件：**映览 0.1.16/build 17，macOS / SwiftUI / Node.js 22.22.2 / SQLite；列表解析不提供海报地址，补图仍依赖豆瓣可访问和精确 ID 匹配。已验证任务链与真实 7 张补图，0.1.17 已在隔离原生窗口验证运行中逐张替换占位，见下文。

## ✅ 记录提交与补图分离，并限制自动补图范围（2026-10-24）

- **环境**：本机 macOS 26.6.2、Apple Silicon、fnm Node.js 22.22.2，映览 0.1.16/build 17；项目最低 macOS 14 不等于本轮在 macOS 14 实测。
- **为何值得记**：增量记录成功、海报地址存在、本地图片存在、S3 镜像存在是不同状态。曾出现增量新增 7 条全部无图，若只补当前数据而不修任务衔接，下次增量仍会复发。
- **最终方案**：[`DoubanService.start/sync`](../../src/douban.js) 在整批提交后返回 `new Set(seen.keys())`；清理已看同步任务后调用 `this.posters.start({ ids: posterIds })`。[`DoubanPosters.start`](../../src/douban-posters.js) 对原候选再按集合过滤，空目标不建任务。沿用既有查询、下载、本地保存和 S3 上传实现，不另写一套补图器。
- **为什么这样做**：增量扫描包括截止当天，但不包括更早条目；使用本次 ID 集合可修复同日已有缺图，同时不扩大到全库。独立补图任务允许记录成功而图片失败，避免图片异常把已提交检查点改回旧值。S3 失败保留本地图片，后续只补上传。
- **关键步骤**：先保留原同步的整批成功边界 → 提取本次 ID → 释放同步任务互斥 → 检查未退出且非离线 → 启动独立补图 → 使用补图自身结果展示失败。同步失败、取消或空集合不触发。
- **易错点**：不能把补图放入记录事务，也不能让补图异常进入已看同步的失败处理；自动调用不带 ID 范围会扩大到旧库。没有海报地址时，反复刷新图片接口或修改 S3 配置不能补出地址。共享原两秒限流，访问限制停止，不循环重试。
- **验证命令原文**：以下为修复轮实际执行的回归命令，本轮重新核对留存日志；不是本轮重新运行结果。应在项目根执行，输出目录须已存在。

```sh
eval "$(fnm env --shell zsh)" && fnm use 22.22.2 && npm test > test-output/douban-auto-poster-tests.log 2>&1 && npm run check && scripts/test-macos.sh > test-output/douban-auto-poster-swift.log 2>&1
```

- **验证证据**：Node 输出 `# tests 110`、`# pass 110`、`# fail 0`；Swift 输出 `Test run with 33 tests in 2 suites passed after 0.024 seconds.`。新增测试位于 [`douban-posters.test.js`](../../test/douban-posters.test.js)，覆盖增量接续、本次范围、S3 镜像、403 后保留记录与进度、同日恢复及已缓存不重复请求。
- **真实验证边界**：真实定向补图结果 `"total": 7`、`"processed": 7`、`"saved": 7`、`"unmatched": 0`、`"error": null`；7 个目标均有本地缓存和镜像引用，原生界面实际显示海报。真实修复使用限定 ID 的生产补图流程，未再次执行真实增量；自动接续由模拟完整链路证明。上传成功与镜像引用不等于本轮逐对象远端回读校验。
