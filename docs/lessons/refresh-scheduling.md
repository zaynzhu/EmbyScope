# 自动更新的负载与暂停边界

**结论速览：**总开关默认关闭；开启后不仅有轻量更新，还可能触发全库校准、首次建库及极影视季集补齐，不能承诺只发三个请求。
**适用条件：**当前Service调度与桌面0.1.10；独立强制离线预览不联网，NAS实际CPU/内存影响尚未测量。

## ✅ 按任务分层并让暂停覆盖队列下一次请求（2026-10-23）

- **环境：**Node22.22.2 / SQLite / macOS；同服限流最低2秒。
- **为何值得记：**用户要求不扫库、保持NAS负载低；仅关闭全库周期不能覆盖轻量、启动检查和季任务。
- **最终方案：**继续使用 [Service.sync/tick/startSeasonSync](../../src/service.js) 的独立任务和持久总开关。以下为 [store.js](../../src/store.js) 已执行的默认配置原文：

```sql
INSERT OR IGNORE INTO settings VALUES('automaticUpdates', 'false');
```

- **为什么这样做：**应用每30秒检查到期，不是每30秒请求媒体库。轻量默认60分钟读取Views、Latest最多18条、Resume最多18条；完整校准默认24小时分页读取片库。没有catalog时仍可能首次完整读取；打开总开关遇到旧数据可能很快启动。
- **额外任务：**仅兼容季模式对缺失/过期季信息每批最多20部、批间至少5分钟，通常保留7天缓存；这是自动更新的一部分，不能藏在“轻量无扫库”的表述里。实时播放轮询另见 [播放活动](playback-activity.md)，不随总开关启动。
- **关键步骤：**先确认普通/离线模式 → 核对每服周期和是否已有catalog → 用户开启总开关 → 后端按期检查 → 暂停时下一页/下一任务不再发起。已经发出的请求可能完成。
- **验证证据：**[app.test.js](../../test/app.test.js) 的小时轻量不扫库、每批20部、五分钟间隔、关闭全部自动入口、分页中途暂停等测试均在74项回归中通过；[offline-mode.test.js](../../test/offline-mode.test.js) 验证退出离线仍保持自动关闭且本次操作不联网。
- **易错点：**关闭总开关不禁止用户手动刷新或详情/海报按需请求；窗口失焦只暂停前台实时查看，不等于停止后台片库调度。状态/失败时间与数据更新时间不可混为一谈；401权限失效与普通离线的缓存保留策略不同。
- **交叉验证：**单agent代码/测试复核，原行为验收见 [验收记录](../验收记录.md)；未新增实机请求。

## 🔶 只读请求对实际 NAS 的资源影响（2026-10-23）

- **环境/交叉验证：**目标NAS极空间Z4S，但未获NAS性能采样；单agent边界记录。
- **当前推断：**HTTP GET不会修改媒体文件，但会产生数据库、CPU、网络及可能的存储访问；限流降低峰值，不证明零负载。
- **已到哪一步：**模拟计数、请求间隔和中途停止有测试；没有NAS CPU/内存的前后对照。
- **下一步验证动作：**用户另行授权并提供其熟悉的监控数据后，对单台一次轻量或完整读取记录前中后负载；不擅自访问管理API/SSH。
- **为何值得继续：**更新周期应依据真实库规模和负载，而不是把默认60分钟当普遍最优值。

## ⛔ 把完整校准设为关闭就宣称“没有任何自动读取”（2026-10-23）

- **环境/交叉验证：**早期调度设计，单agent设计审查和自动暂停回归；[设计审查](../设计审查.md) 暂停调度章节。
- **报错原文：**无单一运行异常；被否决的是“仅把完整校准设为手动”即可暂停的方案。
- **稳定片段：**`automaticUpdates`、`fullHours`、`seasonJobs`、`canRequest`。
- **错误原因：**轻量周期、启动tick、季集和已排队分页属于不同入口，单一周期不能控制它们。
- **为何不可再采用：**会在用户认为暂停时仍读取远端；人为暂停若被当作错误还会污染离线状态。
- **替代方案：**本页成功条目的全局门控和每次新请求前检查。
- **判定时效：**当前调度架构；新加后台任务也必须纳入相同暂停约束。
