# 缺集检查的证据范围与按需读取

**结论速览：**用完整单集快照和合并集区间检查同季已观察范围；页面只读缓存，远端读取按剧触发。当前保留现状，不扩展批量或自动全库检查。
**适用条件：**映览 0.1.22/build 23、Node 22.22.2、macOS arm64；算法与模拟链路已验证，真实 NAS 缺集准确性尚未做逐剧对照。

## ✅ 缺少证据应标待确认，合并集必须保留结束编号（2026-10-27）

- **环境：**0.1.22/build 23，Node 22.22.2 / SQLite / SwiftUI；2026-10-27 核对本机 macOS 26.6.2。功能验证发生于 2026-10-26，源码提交 `d8c9c28`。
- **为何值得记：**季数量、最大集号、单集数量和实际收录范围是不同证据；旧缓存丢失合并集结束编号时，单看起始编号会制造缺口。后续新增缓存字段时仍会遇到同类误判。
- **最终方案：**复用 [normalizeItem](../../src/identity.js) 的编号格式标记，再由 [auditSource / compareEpisodeSources](../../src/episode-audit.js) 合并区间、按来源和季号比较。以下为当前规范化源码原文，供修改同一对象时复用：

```js
    ...(item.Type === 'Episode' ? {
      episodeNumberingVersion: 1,
      episodeEnd: item.IndexNumberEnd == null ? null : number(item.IndexNumberEnd) ?? -1,
      virtual: item.IsVirtualItem === true || item.IsMissing === true || item.LocationType === 'Virtual'
    } : {}),
```

- **为什么这样做：**没有版本标记的旧条目不能证明“没有结束编号”；缺少完整快照、异常编号、失败、过期或季号冲突都应停止该来源的缺口判定。特别篇、零号集和虚拟条目不充当正片证据。跨来源关联沿用稳定编号及冲突保护，身份规则详见 [作品归组经验](media-comparison.md)。
- **关键步骤：**先确认快照完整性与格式 → 排除不参与比较的条目并验证编号 → 合并重叠及相邻区间 → 仅比较同季合格来源的已观察范围 → 保留来源、更新时间和待确认原因。
- **适用条件：**检查的是媒体库编号；没有权威总集数、播出信息或物理文件证据时，不推断未观察到的首尾、整季缺失或可播放性。其他来源收录同编号也不证明剪辑版本相同。
- **验证证据：**[episode-audit.test.js](../../test/episode-audit.test.js) 用 E3、E6、重复 E6、E9 和 E4–E5 合并集断言只缺 E7–E8；覆盖旧格式、虚拟条目、坏编号、跨季、跨服同 ID 与冲突归组。2026-10-27 重读保留的 Node 日志：`# tests 140`、`# pass 140`、`# fail 0`；Swift 日志：`Test run with 46 tests in 2 suites passed`。这些为 2026-10-26 的运行结果，本次没有重跑业务测试。
- **易错点：**“范围内连续”不能改为“整季齐全”；待确认数量不能改为缺集数量。新增字段后不能给旧缓存批量补版本标记来消除提示。
- **交叉验证：**单主 agent 的源码、自动测试与原生模拟界面验证；一轮结构性自审见 [设计审查](../设计审查.md)，完整交付证据见 [验收记录](../macOS验收记录.md)。不是多 agent 独立审计。

## ✅ 本地检查与远端单剧读取分开，失败不能被旧成功快照掩盖（2026-10-27）

- **环境：**同上；`Service.readEpisodes`、既有 EmbyClient 分页及同服务两秒限流，桌面原生窗口通过本机 API 读取结果。
- **为何值得记：**检查页轮询、重复点击和失败回退都可能隐式扩大请求或制造“检查成功”的错觉；不能靠前端禁用按钮保证后端请求去重。
- **最终方案：**`GET /api/episode-audit` 只分析缓存；`POST /api/episode-audit/refresh` 启动指定来源、指定剧集任务，返回 202，由前端轮询本地状态。复用 [readEpisodes](../../src/service.js) 的互斥、完整分页保存与一分钟尝试冷却。以下为测试原文中的去重及冷却断言，完整上下文见 [测试](../../test/episode-audit.test.js)：

```js
  assert.equal((await request('/api/episode-audit/refresh', 'POST', body)).status, 202)
  assert.equal((await request('/api/episode-audit')).data.running, true)
  assert.equal((await request('/api/episode-audit/refresh', 'POST', body)).status, 202)
  assert.equal(calls, 1)
  release(); await app.service.drain()
  const result = (await request('/api/episode-audit')).data
  assert.equal(result.running, false)
  assert.equal(result.counts.gaps, 1)
  assert.equal((await request('/api/episode-audit/refresh', 'POST', body)).status, 409)
  assert.equal(calls, 1)
```

- **为什么这样做：**接受任务不等于读取成功；普通读取失败保留旧数据和原成功时间，同时暴露错误并停止缺口判断。普通片库里的旧成功数据不能盖掉显式单剧读取的失败。401 沿用已有授权失效机制，不能承诺所有错误都保留缓存。
- **关键步骤：**校验本机认证、来源、服务器和剧集 → 检查互斥与冷却 → 每次远端请求前校验离线、退出和连接版本 → 完整结果到齐后核对版本再保存 → 前端刷新本地结果。暂停门控的一般机制见 [调度经验](refresh-scheduling.md)。
- **适用条件：**窗口关闭不等于取消已启动的单剧读取；应用退出或离线会阻止后续请求及成功结果回写。既有服务器自动更新是独立机制，不能把“缺集页面只读”描述为“整个应用没有联网”。
- **验证证据：**上述测试、失败快照保留、连接变更、退出、无授权及 API 防护用例均在 140 项回归中通过。隔离原生预览从待确认变为缺 E3、E5，并展示另一来源已有对应编号；重复点击显示冷却。2026-10-27 重读模拟请求日志只有一条 `/Shows/series/Episodes`；详细界面证据引用验收记录，未重新操作真实服务。
- **易错点：**不要把页面轮询接到远端刷新接口；不要为了清空待确认而自动读取所有剧集；两秒限流只限制频率，不证明请求总量或 NAS 负载很小。
- **交叉验证：**单主 agent 的服务端回归、Swift 状态测试及隔离原生模拟；审查和验收入口同上。模拟数据不构成真实 NAS 准确性证据。

## 🔶 真实剧集结果与资源负载仍需限定样本验证（2026-10-27）

- **环境 / 交叉验证：**0.1.22/build 23，真实本地缓存只读分析及正式版界面由单主 agent 核验；没有本轮真实单剧读取或 NAS 性能采样。
- **已到哪一步：**2026-10-27 重读只读分析报告：2,105 个分组全部待确认、106 页、177 ms。该耗时只代表一次本机缓存计算；不能推算远端全库扫描耗时、负载或缺集数量。原报告与日志位于本机忽略目录 `test-output/episode-audit-20261026/`，跨机器复用以仓库中的测试和验收记录为证据入口。
- **当前推断：**真实接口的编号或元数据质量可能影响结果；增加读取范围会增加请求，但具体增量及 NAS 压力没有测量。不将“全库扫描负担太大”标成已复现性能故障。
- **下一步验证动作：**仅在用户再次提出实际需求并授权范围后，选其已知完整或缺集的具体剧集，执行一次按需读取并逐项对照；不自动恢复批量扫描任务。
- **为何值得继续：**如果用户实际遇到误报，限定样本可以区分编号规则、缓存不足和接口数据问题；当前没有必须继续探索的任务。

## 当前产品边界（2026-10-27 用户决定）

用户明确表示此块先保持现状，先正常使用再决定下一块。暂不做批量读取或自动全库缺集扫描，也不为消除待确认而反复读取。此处记录的是产品决定，不是技术不可行或性能实测结论；后续需求变化时再重新评估。
