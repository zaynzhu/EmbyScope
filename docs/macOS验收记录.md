## 内存与查询开销

测量不是长期运行保证，也不是其他机器的基准。RSS 与 macOS physical footprint 口径不同，不混用；独立进程峰值发生时间不同，不能相加当作整体同时峰值。

| 样本 | 观测 |
| --- | --- |
| 小型演示初轮交互后，`vmmap -summary` | App physical footprint 53.6M、Node 27.7M，当前相加约 81.3M |
| 新一轮小型演示连续 20 轮分页／页面切换后 | App 63.3M、Node 26.7M，当前相加约 90.0M；各自历史峰值 71.4M / 54.0M |
| 10,000 条模拟记录，5,000 分组，连续请求 20 页，优化前 | 每页 68.4–91.5 ms；离散 RSS 采样最大 219.4 MiB，最后 202.4 MiB |
| 同规模、同操作，复用单次请求 catalog 解析后 | 每页 31.3–48.8 ms；离散 RSS 采样最大／最后 206.1 MiB；首页计算 62.1 ms，返回最近 24 条 |

规模样本通过临时 SQLite 写入每服 5,000 个模拟电影，分别使用相同 TMDB 编号形成 5,000 组；调用 `Service.library` 的第 1 至 20 页，每页 24 条。用 `performance.now()` 和 `process.memoryUsage().rss` 在每次请求后采样，无图片、无远端请求。数据生成本身影响进程内存，没有强制 GC，不测连续峰值。小型 UI 样本重复使用两张封面，不能代表数千张不同真实海报。

改进只复用同一次同步计算内已经解析的缓存，不改变去重逻辑，也不把全库长期驻留。**Node 仍在分页前处理整个所选片库，内存还有增长；尚不能证明真实大库长期常驻占用稳定。** 后续应先用获准的真实库和更丰富图片实测，再决定是否需要结构化 SQLite 查询或其他优化。
