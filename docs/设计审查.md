# 结构性决定的对抗性审查

审查对象：单服务、普通 Emby 账号、缓存汇总与跨服作品去重。角色：资深工程师与安全研究员。日期：2026-10-17。

## 🔴 致命弱点

**普通账号不等于管理员数据源**

- 问题：照搬 TTD 的全站播放次数、观众或趋势，会把管理数据权限误当作所有账号具有的能力。
- 为什么致命：统计口径虚假，失败值还容易被渲染成零。
- 反例 / 证据：普通用户视图、继续观看与全站历史不是同一数据集合；403 无法证明集合为空。
- 处理：只走用户级读取接口，按区块记录可用性；没有可信历史的指标显式不可用。

**编号关联会产生传递冲突**

- 问题：A 与 B 同 TMDB，B 与 C 同 IMDb，但 A 与 C 的另一编号不同；逐条贪心合并依赖顺序。
- 为什么致命：不同作品被错误折叠，合计无法解释。
- 反例：A={TMDB:1,IMDb:2}，B={TMDB:1}，C={IMDb:2,TMDB:3}。
- 处理：先形成编号连接组件，再检查组件内每类编号是否唯一；冲突组件全部独立保留。缺失编号不按名称归并。

## 🟡 主要缺陷

| 缺陷 | 严重程度 | 处理 |
|---|---|---|
| 网络失败保留旧数据可能混淆权限撤销 | 高 | 网络失败标旧缓存；401清全部，403清受影响区块，页面标更新时间 |
| 换账号时在途旧请求回写 | 高 | 连接 revision 守卫，变更后立即清缓存，旧任务禁止回写 |
| 分页读取过程中媒体数量变化 | 中 | 校验总数和重复 ID，全量成功后才替换；无法提供服务器事务快照，不声称强一致 |
| 海报请求泄露令牌或成为任意代理 | 高 | 仅后端请求、固定路径、已知条目鉴权、不跟随跳转、限制格式 / 大小 |
| 加密密钥与数据库同目录 | 中 | 明确保护范围，整个目录泄露仍可解密；文件0600，密钥丢失拒绝重建 |
| 两秒间隔导致首次大库同步和海报较慢 | 中 | 后台独立同步，返回缓存，显示同步状态和时间，不以假数据填充 |
| 单次全量 JSON 缓存的大库内存成本 | 中 | 分页抓取与100万条安全上限；适合个人看板，不宣称无限库容量 |

## 🟢 改进建议

1. 为权限、离线、传递冲突、内部相同编号、旧任务回写加入真实 HTTP 模拟测试。
2. 将公开 DTO 限定为明确字段，不回传原始 Emby 响应、资源路径、令牌或用户名。
3. 在干净云端 runner 导入同一个 tar，禁止拉取和构建，从包内 Compose 验收启动与持久化。
4. 真实 Emby 验证单独记录，不能用模拟结果或 TTD 正常运行替代。

## 📋 审查总结

- 整体评估：该架构适合单管理员自用；数据可用性和去重冲突必须成为明确产品语义。
- 最高优先级行动：用测试固定“缺失不是零”“相同内部 ID 不串服”“编号冲突不合并”。
- 如果不改：看板会产生可信外观下的错误统计，并可能显示旧账号无权读取的数据。

## 极影视兼容修复的补充审查（2026-10-17）

### 🔴 致命弱点

- 登录成功不能证明整个兼容协议完整。实机在限定类型查询中返回了未请求的类型，不能把“未读取到单集”解释成“单集为零”。
- 不将一次设备观察推广为所有极影视版本，也不以自报 Emby 版本识别供应商。限制判定基于每次实际缓存中是否含有查询未请求的类型。

### 🟡 主要缺陷

| 缺陷 | 严重程度 | 简要说明 |
|---|---|---|
| 返回空数组的含义不明 | 中 | 可能无内容，也可能兼容层未实现；不能凭空补造最近入库或观看记录 |
| 全量遍历每部剧获取季集 | 中 | 需要大量受限速约束的请求，且没有完整协议证据，不在本次修复中盲目添加 |

### 🟢 改进建议

1. 补充兼容头且保留原标准头，回归验证标准 Emby 和严格兼容层。
2. 已读取片库继续可用，明确标识覆盖范围；不可信的单集总数设为不可用，并传播到汇总和详情。
3. 原始服务端响应不进入客户端或日志，测试只使用合成响应，不使用实机凭据或私有作品内容。

### 📋 审查总结

- 整体评估：可修复认证兼容并提供已知范围的数据展示，尚不能声称极影视接口完全等价于 Emby。
- 最高优先级行动：禁止将兼容接口缺失的单集数据误报为零。
- 如果不改：登录状态正常的看板仍会给出错误的完整统计。

## 服务器筛选与 NSFW 海报补充审查（2026-10-17）

### 🔴 致命弱点

- 汇总作品可能来自多服，不能只按第一来源决定虚化：任一来源带 NSFW 标签就默认虚化。详情和概览也必须使用同一判定。
- 虚化只是本地显示偏好，不是权限控制；不能声称图片未传到浏览器。刷新页面重新启用虚化，单张解锁键包含服务器与条目 ID。

### 🟡 主要缺陷

| 缺陷 | 严重程度 | 处理 |
|---|---|---|
| 旧数据库没有标签字段 | 高 | 启动时增量添加默认关闭的布尔字段，保留连接和缓存 |
| 重新开启虚化仍残留单张解锁 | 高 | 全局重新开启时清除全部单张解锁记录 |
| 片库顶部筛选不明显 | 中 | 片库筛选表单内增加服务器选择，与顶栏联动并重置分页 |

### 🟢 改进建议

1. 标签由用户显式设置，不按服务器名或作品标题猜测。
2. 首次点击虚化海报只解除虚化，标题和来源标签仍直接打开详情。
3. 用模拟数据验证混合来源、相同 ItemId、分页、重新遮挡与数据库持久化。

### 📋 审查总结

- 整体评估：可用小范围数据库迁移与统一海报渲染实现，不需要独立服务。
- 最高优先级行动：防止汇总和详情绕开用户设置的虚化。
- 如果不改：同一作品在不同页面可能暴露未遮挡海报。

## 极影视分类与季集补全方案审查（2026-10-17）

### 🔴 致命弱点

- `SortName` 返回 3374 条，而无排序查询声称 3418 条；后续逐页实测发现独立类型查询同样漏掉容器且总数不一致，不能将 3418 当成已验证作品数。最终回退到用户 Views + ParentId 逐库、逐合集读取，每个目录校验总数和 ID；列表 Folder 的类型用详情确认。
- 单次季数或 `Series.ChildCount` 不能代替单集总数。仅汇总每个季接口返回的非负整数 `Season.ChildCount`；字段缺失、权限异常或尚未核对必须明确为未知。

### 🟡 主要缺陷

| 缺陷 | 严重程度 | 处理 |
|---|---|---|
| 数千部剧逐个核对需要一小时以上 | 高 | 独立后台补全、逐剧持久缓存、显示进度并支持重启续查，不能阻塞主片库 |
| 单集详情部分请求超时 | 高 | 按需请求并单独记录错误，不影响季数统计和电影片库 |
| 补全周期超过通常缓存周期 | 中 | 季集计数缓存至少 24 小时，显示最旧核对时间；失败限频重试 |
| 使用旧账号季集结果 | 高 | 复用连接 revision 守卫，换账号清全部缓存，401/403清受影响数据 |

### 🟢 改进建议

1. 标准 Emby 保持递归完整读取路径；仅实际类型异常时进入兼容路径，不以服务器版本或名称猜测。
2. 兼容计数标明「按季接口集数汇总」，同时返回已核对剧集数和总剧集数。
3. 复现排序遗漏、分页异常、缺少计数字段、403、单集超时和恢复续查。

### 📋 审查总结

- 整体评估：通过目录遍历修复分类读取；全量集数需要异步核对，无法承诺立即完成。
- 最高优先级行动：先让逐目录分页、循环合集去重和真实计数来源通过测试，再启动实机补全。
- 如果不改：要么继续漏作品，要么把尚未获取的单集误报为零。
