# 结构性决定的对抗性审查

## TTD 实时状态出口路线复核（2026-10-23）

### 🔴 致命弱点

- 将“有 OpenAPI”当作“有极影视实时出口”不成立：目录只确认绑定看板的 live 与代理历史记录，参数说明亦非完整规范，不能臆造规则参数。
- 将普通 Python 插件当成请求钩子不成立：文档为独立进程 run 任务，未提供业务请求观察协议。不能靠安装插件的名义修改运行进程。

### 🟡 主要缺陷

| 缺陷 | 处理 |
|---|---|
| 目录未列出就断言绝无能力 | 结论限定为当前公开且已确认的入口，不枚举私有路径 |
| 用管理员 OpenAPI Token 冒充只读认证 | 不创建、复制或持久化；新出口要求单独限制权限 |
| 新代理被称为无影响的旁路 | 经过它的客户端新增依赖，必须说明地址变化、失效与回退，并另行批准 |
| 观察到进度却缺少认证用户及规则 | 取得可验证绑定后才接入，不能只按 ItemId 或用户名归属 |

### 🟢 改进建议

1. 准备最小状态出口需求，优先由 TTD 在既有校验后提供受限读取，不改播放器路径。
2. 无实现维护方时才讨论独立测试入口，先确认用户接受范围，不能直接改现有反代。
3. 在真实出口可读前明确未完成，不提交无真实来源的看板功能。

### 📋 审查总结

- 整体评估：已缩小外部能力缺口，尚没有可交付的极影视实时数据源。
- 最高优先级行动：确定由谁提供受支持的事件出口，或取得独立测试入口的设计许可。
- 如果不改：映览只能显示不可用；强行用取链历史补齐会误导用户。

## PlaybackInfo 后 302 成功的结论审查（2026-10-19）

### 🔴 致命弱点

- 只测静态流省略了常见客户端播放信息流程，不能把回退结果推广为 TTD 与极影视整体不兼容。本次完整接口流程实际得到 302 与有效媒体片段，修正先前未完成的结论。
- 本次接口成功不代表原生极影视客户端已经经过代理。客户端入口尚未提供，不能宣称用户最终播放目标全部完成。

### 🟡 主要缺陷

| 缺陷 | 严重程度 | 处理 |
|---|---|---|
| 失败与成功对照相隔多个小时 | 高 | 不断言缺少 PlaybackInfo 是唯一根因，记录时间及缓存命中证据 |
| 账号状态显示剩余时间为 0 | 中 | 不等于刷新令牌失效，不自动刷新或更换账号 |
| 1 KB 读取只证明当前链接可用 | 中 | 保留客户端解码、持续播放和其他资源的未验证项 |

### 🟢 改进建议

1. 保留已成功的配置，不为用户枚举测试的 404 增加伪造接口或固定凭据注入。
2. 取得用户实际客户端入口，再用对应播放时间、条目和 HTTP/日志证据核对路由。

### 📋 审查总结

- 整体评估：该样本的代理 302 接口链路成功；无需以获取源码或部署适配层为前置条件。
- 最高优先级行动：验证实际原生播放器路径。
- 如果不改：可能继续改造已可用的代理，或将诊断请求成功误报为原生播放成功。

## STRM 对照结果的结论补充（2026-10-19）

### 🔴 致命弱点

- TTD 地址直接 302 成功不等于极影视反代成功：同一资源的反代响应仍为 206。不能省略入口差异或将两条测试拼成不存在的完整成功链路。
- 两条规则运行不能证明所有并发取链逻辑无缺陷。只排除“配置层只接受一条规则”的解释，不用停止正常规则来做破坏性对照。

### 🟡 主要缺陷

| 缺陷 | 严重程度 | 处理 |
|---|---|---|
| 回退日志没有具体取链失败阶段 | 高 | 获取准确镜像版本的实现或针对性诊断证据，再决定适配方式 |
| 1 KB 文件头不等于持续播放验收 | 中 | 仅报告取样有效，不声称已验证整部视频 |
| 无日志被误当成无重定向 | 高 | 记录实际 302 及直链响应，日志只作关联证据 |

### 🟢 改进建议

1. 请用户提供当前镜像完整名称和标签，先确认源码可得性，不修改 NAS 或现有服务。
2. 将未确认环节保持为未知，不先注入固定凭据或伪造兼容接口。

### 📋 审查总结

- 整体评估：该光鸭资源的 TTD 直接取链可用，极影视反代取链过程仍待定位。
- 最高优先级行动：定位实际取链实现与失败阶段。
- 如果不改：可能为错误原因开发适配层，并误报 302 全链路成功。

## 既有反代播放实证的结论审查（2026-10-19）

### 🔴 致命弱点

- 用一个 ISO 元数据样本推断所有极影视 STRM 不兼容，证据不足。该样本只确认原始流回退，下一步必须使用用户确认的 TTD STRM 样本。
- 206 与成功解码、302 云盘直链是不同验收条件。本轮没有读取完整媒体或启动播放器，不能声称实际播放验收完成。
- 为匿名请求统一补固定 UserId / Token 会越过认证边界。诊断只补充同一次正常登录取得的真实身份，不构成可部署的适配层。

### 🟡 主要缺陷

| 缺陷 | 严重程度 | 处理 |
|---|---|---|
| 同时补 Token 与 UserId，无法区分两者各自作用 | 中 | 只报告组合请求成功，不推断单独哪个字段足够 |
| 测试按钮依赖用户枚举，播放却可以回退原始流 | 高 | 分别记录测试、登录、详情、流响应，不将一个环节结果代替其他环节 |
| 未获得原生播放器入口或路由证据 | 高 | 19000 的诊断结果不推广到用户平时的原生播放路径 |
| 没有 302 日志可能只是取链失败 | 中 | 将对应条目日志与响应状态、Location 联合验证 |

### 🟢 改进建议

1. 先取得一条用户确认的 TTD STRM 样本，只在已授权入口定点读取，不扫库寻找。
2. 如获得 302，仅在确认目标范围和认证头隔离后验证有限媒体读取；不能将媒体令牌转发给第三方。
3. 有明确失败阶段和接口证据后再决定是否适配，保留现有工作配置。

### 📋 审查总结

- 整体评估：已证明现有反代的登录与单条目读取可用，以及本样本回退原始媒体响应；未证明 STRM 302 成败。
- 最高优先级行动：取得确认来自 TTD 的 STRM 样本。
- 如果不改：直接部署认证转换或伪造用户列表可能只掩盖错误，不能保证实际直链播放。

审查对象：单服务、普通 Emby 账号、缓存汇总与跨服作品去重。角色：资深工程师与安全研究员。日期：2026-10-17。

## 🔴 致命弱点

**普通账号不等于管理员数据源**

- 问题：照搬 TTD 的全站播放次数、观众或趋势，会把管理数据权限误当作所有账号具有的能力。
- 为什么致命：统计口径虚假，失败值还容易被渲染成零。
- 反例 / 证据：普通用户视图、继续观看与全站历史不是同一数据集合；403 无法证明集合为空。
- 处理：只走用户级读取接口，按区块记录可用性；没有可信历史的指标显式不可用。

**编号关联会产生传递冲突**

- 问题：A 与 B 同 TMDB，B 与 C 同 IMDb，但 A 与 C 的另一编号不同；逐条贪心合并依赖顺序。
- 为什么致命：不同作品被错误折叠，合计无法解释。
- 反例：A={TMDB:1,IMDb:2}，B={TMDB:1}，C={IMDb:2,TMDB:3}。
- 处理：先形成编号连接组件，再检查组件内每类编号是否唯一；冲突组件全部独立保留。缺失编号不按名称归并。

## 🟡 主要缺陷

| 缺陷 | 严重程度 | 处理 |
|---|---|---|
| 网络失败保留旧数据可能混淆权限撤销 | 高 | 网络失败标旧缓存；401清全部，403清受影响区块，页面标更新时间 |
| 换账号时在途旧请求回写 | 高 | 连接 revision 守卫，变更后立即清缓存，旧任务禁止回写 |
| 分页读取过程中媒体数量变化 | 中 | 校验总数和重复 ID，全量成功后才替换；无法提供服务器事务快照，不声称强一致 |
| 海报请求泄露令牌或成为任意代理 | 高 | 仅后端请求、固定路径、已知条目鉴权、不跟随跳转、限制格式 / 大小 |
| 加密密钥与数据库同目录 | 中 | 明确保护范围，整个目录泄露仍可解密；文件0600，密钥丢失拒绝重建 |
| 两秒间隔导致首次大库同步和海报较慢 | 中 | 后台独立同步，返回缓存，显示同步状态和时间，不以假数据填充 |
| 单次全量 JSON 缓存的大库内存成本 | 中 | 分页抓取与100万条安全上限；适合个人看板，不宣称无限库容量 |

## 🟢 改进建议

1. 为权限、离线、传递冲突、内部相同编号、旧任务回写加入真实 HTTP 模拟测试。
2. 将公开 DTO 限定为明确字段，不回传原始 Emby 响应、令牌或用户名；片库列表不含资源路径，后续资源详情只按白名单返回本地路径。
3. 在干净云端 runner 导入同一个 tar，禁止拉取和构建，从包内 Compose 验收启动与持久化。
4. 真实 Emby 验证单独记录，不能用模拟结果或 TTD 正常运行替代。

## 📋 审查总结

- 整体评估：该架构适合单管理员自用；数据可用性和去重冲突必须成为明确产品语义。
- 最高优先级行动：用测试固定“缺失不是零”“相同内部 ID 不串服”“编号冲突不合并”。
- 如果不改：看板会产生可信外观下的错误统计，并可能显示旧账号无权读取的数据。

## 极影视分类与季集补全方案审查（2026-10-17）

### 🔴 致命弱点

- `SortName` 返回 3374 条，而无排序查询声称 3418 条；后续逐页实测发现独立类型查询同样漏掉容器且总数不一致，不能将 3418 当成已验证作品数。最终回退到用户 Views + ParentId 逐库、逐合集读取，每个目录校验总数和 ID；列表 Folder 的类型用详情确认。

### 🟡 主要缺陷

| 缺陷 | 严重程度 | 处理 |
|---|---|---|
| 数千部剧逐个核对需要一小时以上 | 高 | 独立后台补全、逐剧持久缓存、显示进度并支持重启续查，不能阻塞主片库 |

2. 兼容计数标明「按季接口集数汇总」，同时返回已核对剧集数和总剧集数。

### 📋 审查总结

- 整体评估：通过目录遍历修复分类读取；全量集数需要异步核对，无法承诺立即完成。
- 最高优先级行动：先让逐目录分页、循环合集去重和真实计数来源通过测试，再启动实机补全。

## 资源位置、重复条目与低负载更新审查

### 🔴 致命弱点

- 编号重复只证明同一作品的多个条目，不证明相同文件、相同版本或可安全删除。明确标记条目数及额外条目数，冲突仍独立保留，不提供删除操作。
- 原始 MediaSources 可包含签名 URL、令牌和认证信息。只提取绝对本地路径，远程地址不回传；不探测文件是否存在，不把容器挂载路径称为 NAS 物理路径。
- Latest 不包含完整删除与变更事件，不能用它冒充可靠增量同步。小时任务只更新轻量区块，完整计数与去重依赖最近完整校准，默认每天一次并允许关闭自动校准。

### 🟡 主要缺陷

| 缺陷 | 处理 |
|---|---|
| 展开重复组引发大量详情请求 | 只按用户点击读取单条资源路径，已读缓存复用 |
| 修改标签和周期意外重扫 | 非账号修改不触发远端同步 |
| 季集补全连续请求数千次 | 每批最多 20 部、两批至少 5 分钟、已完成计数缓存至少 7 天 |
| 远端负载未知 | 不宣称 NAS 内存有实测结论；维持串行请求、限速、分页、失败冷却 |

### 🟢 改进建议

1. 分开显示完整片库更新时间与轻量数据更新时间，手动完整校准有明确按钮。
2. 服务器可设置轻量周期和完整校准周期，普通刷新不扫库。
3. 测试路径脱敏、跨服重复、编号冲突、每小时无 catalog 请求、配置更新不请求远端、分批重启续查。

### 📋 审查总结

- 整体评估：只读排重辅助成立，重复作品不等于重复文件。
- 最高优先级行动：消除小时全库重读和原始资源响应泄露。
- 如果不改：定位信息可能泄露访问凭据，周期刷新持续增加 NAS 请求负载。

## 暂停调度与 TTD 诊断边界审查（2026-10-18）

### 🔴 致命弱点

- 仅把完整校准设为手动仍会留下轻量轮询、启动同步和季集任务，不能称为暂停。总开关必须持久化并覆盖所有自动入口和排队中的下一次请求；不将人为暂停误报为服务端离线。
- TTD 测试返回 400、正文为 HTTP 404，只能证明错误来自后端测试流程，不能凭此认定上游路径、请求方法或 Token 错误。公开仓库旧版源码不能代替运行中的新版实现。
- 为所有匿名请求注入固定用户 Token 会绕过认证；即使测试通过，也不能证明 302 播放正确，更不能证明极影视原生播放器经过 TTD。

### 🟡 主要缺陷

| 缺陷 | 处理 |
|---|---|
| 周期藏在连接编辑里难发现 | 服务器设置页独立总开关及各服周期表单 |
| HTTP GET 被误认为零负载 | 明确仍有数据库、CPU、网络和可能的存储访问；无 NAS 性能实测则不承诺零影响 |
| 取消时仍有在途请求 | 允许在途响应收尾，但后续自动分页与排队请求禁止发出，保留旧完整缓存 |
| 隔离测试记录真实凭据 | 使用固定假凭据，诊断器仅记录字段名、方法与路径，不转发媒体、不保存请求体 |

### 🟢 改进建议

1. 用请求计数验证暂停、重启持久化、显式恢复、分页中途停止与手动读取的边界。
2. 现有 TTD 配置和端口不动；只有拿到真实请求证据，才讨论有限适配。
3. 定点访问 NAS 媒体接口与隔离测试先按用户要求取得明确授权。

### 📋 审查总结

- 整体评估：暂停调度可以直接实现，兼容适配仍依赖具体协议证据。
- 最高优先级行动：先停止后台读取，避免以猜测接口的方式继续探测。
- 如果不改：可能破坏现有播放链路，或让用户误以为无后台负载。

## 关联反代与播放会话（2026-10-21）

### 🔴 致命弱点

- 把反代地址当作服务器会双计片库，且相同 ItemId 可能错配。反代只保存于现有 `servers.proxyUrl`，不创建连接、缓存命名空间或同步任务；已登记的原地址和反代地址不能再归属另一连接。不自动猜测未登记的别名。
- 一条 302 日志只能证明发生过请求，不能证明持续观看。当前日志样本缺少明确规则归属，不能只按同名或 ItemId 关联；本轮不实现不可靠的 TTD 自动日志归档。

### 🟡 主要缺陷

| 缺陷 | 影响 | 处理 |
| --- | --- | --- |
| 会话接口可能返回其他用户 | 泄露非当前账号信息 | 按登录 UserId 精确过滤，仅输出白名单字段 |
| 客户端停止上报或缓存过期 | 将旧会话误标正在播放 | 心跳缺失／超过90秒不确认播放；快照超过60秒或请求失败后状态未知 |
| 普通账号权限和兼容层不同 | 无法统一提供实时信息 | 401／403／404分别提示；不伪造空闲状态、不扫描猜接口 |
| 填入反代地址不等于取得日志权限 | 错用 Emby Token 或浏览器 Cookie | 不向反代转发令牌，不复制浏览器认证信息；TTD长期认证尚未接入 |

### 🟢 改进建议

1. 默认仅手动读取原地址 `/Sessions`，30秒请求冷却，共用原限流器；不启动后台轮询、播放上报或远程控制。
2. 离线允许独立的本地反代关联操作，但继续禁止远端读取；此接口忽略其他配置字段，不能借机更换账号或地址。
3. 通过模拟数据覆盖过期、权限不足、两服隔离、账号切换竞争；真实接口只执行已授权的有限验证。

### 📋 审查总结

关系建模可落地，但当前数据不足以接入可信的 TTD 分服务器播放日志。最高优先级是守住服务器身份与会话时效；否则首页会产生重复计数或虚假的“正在观看”。
